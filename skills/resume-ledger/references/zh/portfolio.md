# 作品集方法（zh）

作品集回答的是"你怎么想、怎么取舍、怎么验证"，不是功能清单。每册讲一个项目，一个主机制讲透。

## 结构（旗舰 8 页封顶，短篇 3 页）

旗舰：概览 → 这个项目改变了什么（之前 / 之后 / 凭什么说）→ 问题与目标（成功标准）→ 方案与取舍（含一个主动推翻过的首选）→ 深挖一个机制 → 评测与上线（含"数字的边界"）→ 人在回路与合规 → 结果数据 → 决策记录 → 复盘（做对了什么 / 会改什么）→ 技术栈 → 下一步与未解决的问题 → 常见问题。
短篇：背景与问题 → 成功标准 → 方案与关键决策 → 分工边界 → 结果 → 复盘。

一个让读者记住的办法：加一节"一条数据 / 一个请求的一天"，把机制走一遍，并点明 AI 出现在哪一步。

## 三条硬约束
- 数字由确定性系统算、模型只做解释或改写；每个 AI 参与决策的环节写清谁能确认或推翻。
- 先说未完成和风险，再说成果；"数字的边界"一节必须有。
- 规划项一律写在"下一步"，不计入成果。

## 数字
- 口径可以与简历不同，但每个数字仍要有 scope 为 portfolio 或 both 的账本行；`check_numbers.py` 会按 portfolio 范围对账。
- 真实日期不写，用相对月份："第 1 个月立项"；时间起点在概览里说明。
- 同环比与实验结论分开写；没有对照组就明说。

## 去识别化清单（发出前逐条过）
- 姓名、雇主、客户名、合作方名
- 真实日期、内部版本号、系统代号
- 业务线名称与条数、团队人数（写"核心团队"）
- 可推断行业或地区的场景词
- 供应商名（AI 工具与模型厂商除外）
- 联系方式
`scan.py --portfolio` 会扫姓名、邮箱、电话、真实日期；场景词靠人工。

## 常见失误
- 把作品集写成简历的扩写：同一组数字换个顺序再说一遍。
- 只写成功：没有推翻过的方案、没有未解决的问题，读者不信。
- 口径与简历相互矛盾又不能解释：简历"直接负责 4 人小组"、作品集"核心团队"，面试要能接上。
